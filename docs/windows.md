# ScaleGuard на Windows

## Как это работает

Windows-версия использует **тот же UI и тот же VPN-движок**, что Android и
Apple. Отличие только в том, как ядро получает трафик:

```
Flutter UI
   │
   ▼
lib/core/engines/windows_vpn_engine.dart
   │ 1. генерирует config.yaml (lib/core/mihomo_config.dart)
   │ 2. запускает windows/runner/mihomo.exe как дочерний процесс
   │ 3. ждёт готовности RESTful-контроллера на 127.0.0.1
   │ 4. переключает системный прокси Windows либо включает TUN
   ▼
mihomo.exe ──► системный прокси (WinINet)  ─┐
            └─► TUN-адаптер (Wintun, mixed) ─┴─► интернет
```

Ядро вынесено в отдельный процесс намеренно:

* приложение **не содержит кода mihomo**, поэтому не является производной
  работой GPL-3.0 (см. `windows/runner/NOTICE.txt`);
* падение ядра не роняет окно, а ядро можно обновлять отдельно;
* один и тот же бинарник используется и в отладке, и в поставке.

## Режимы подключения

В настройках подключения выбирается один из трёх режимов:

| Режим | Охват | Права | Когда использовать |
|-------|-------|-------|--------------------|
| **По правилам** (по умолчанию) | Весь трафик машины через локацию, российские сайты — напрямую | требует запуска от имени администратора | обычный режим работы |
| **Весь трафик** | Весь трафик машины через локацию, включая российские сайты | требует запуска от имени администратора | когда нужен иностранный адрес на всех сайтах |
| **Системный прокси** | Браузеры и приложения, работающие через WinINet: Edge, Chrome, Office, большинство .NET-приложений | не требует администратора | когда прав администратора нет |

Два первых режима используют один и тот же туннель и различаются только
флагом «российские сайты — напрямую», поэтому переключение между ними
применяется к живому соединению без переподключения. Системный прокси — другой
режим платформы, при переходе в него туннель перезапускается. Выбор хранится в
Credential Manager (`ScaleGuard:tunnel_mode` и `ScaleGuard:ru_direct`).

Системный прокси включается записью в
`HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` и вызовом
`InternetSetOption(INTERNET_OPTION_SETTINGS_CHANGED | INTERNET_OPTION_REFRESH)`,
иначе Windows не перечитает настройки до следующего входа в систему. Прежние
значения сохраняются до подключения и восстанавливаются при отключении —
в том числе если ядро упало (`lib/core/windows_system_proxy.dart`).

## Сборка

Flutter требует компонент Visual Studio **«C++ CMake tools for Windows»**, для
установки которого нужны права администратора. Там, где его нет, сборка
выполняется скриптом, который делает те же шаги standalone-CMake и Ninja:

```powershell
cd "ScaleGuard Mobile App"
tool\build_windows.bat debug     # или release
```

Скрипт:

1. подготавливает артефакты движка Flutter в `windows/flutter/ephemeral`
   (`tool/stage_flutter_artifacts.ps1`) — обычно это делает `tool_backend.bat`;
2. конфигурирует CMake с генератором Ninja и компилятором MSVC
   (окружение берётся из `vcvars64.bat`);
3. собирает цель `install`, чтобы рядом с `.exe` появились
   `flutter_windows.dll`, `icudtl.dat` и `data/flutter_assets`;
4. копирует ядро в `<out>\core\mihomo.exe` — именно там его ищет движок.

Результат: `build\windows\x64\debug\runner\ScaleGuard.exe`.

Если в системе установлен компонент CMake для Visual Studio, работает и
штатный путь:

```powershell
flutter build windows --release
```

## Сборка ядра

```powershell
cd build-tools\mihomo-build
$env:GOPROXY='https://proxy.golang.org,direct'
$env:CGO_ENABLED='0'
go build -tags with_gvisor -trimpath `
  -ldflags "-s -w -X main.version=1.0.0" `
  -o "..\..\ScaleGuard Mobile App\windows\runner\mihomo.exe" .
```

* `-tags with_gvisor` включает userspace-стек gVisor, без него TUN-режим не
  работает.
* `CGO_ENABLED=0` корректен: `sing-tun` **встраивает wintun.dll и загружает её из
  памяти**, поэтому рядом с `.exe` ничего докладывать не нужно — вопреки тому,
  что пишут про старые форки Clash. Копия `windows/runner/wintun.dll` всё равно
  кладётся рядом с ядром при сборке: она ничего не ломает, зато раскладка
  каталога `core` на чистой сборке совпадает с той, на которой TUN проверялся.
* Версия ядра задаётся `-X main.version=...`; сама сборка mihomo — в
  `build-tools/mihomo-build/go.mod`.

### Контрольные суммы ядра

Вместе с бинарником собирается манифест `windows/runner/SHA256SUMS`, который
попадает в `core` рядом с ядром. Перед запуском TUN (то есть до того, как ядро
получит права администратора) клиент сверяет хеши. Расхождение — ошибка, а не
предупреждение: подключение в режиме TUN не выполняется, системный прокси
продолжает работать. После замены ядра или `wintun.dll` манифест нужно
пересобрать:

```powershell
dart run tool\write_core_manifest.dart
```

Проверка:

```powershell
.\windows\runner\mihomo.exe -version
dart run tool\smoke_core.dart            # парсер, генератор конфига, прокси
dart run tool\smoke_core.dart --engine   # сквозной прогон движка
```

## Разделение зависимостей по платформам

Две популярные библиотеки тащат C++-код под Windows, которому нужны заголовки
ATL (отдельный компонент Visual Studio). Чтобы сборка не требовала лишнего,
в `pubspec.yaml` подключены `dependency_overrides` на локальные пакеты из
`tool/shims`:

| Пакет | Что сделано | Где реализация |
|-------|-------------|----------------|
| `flutter_local_notifications` | Windows-версия заменена на no-op на Dart; напоминания не падают, а просто не показываются | реальные напоминания — `lib/services/notification_backend_mobile.dart` |
| `flutter_secure_storage` | токен хранится в **Windows Credential Manager** через `dart:ffi` (шифруется ОС, привязан к учётной записи) | `tool/shims/flutter_secure_storage/lib/src/windows_credential_vault.dart` |

Если у вас установлен компонент ATL, оба override можно удалить — код
приложения от этого не изменится.

## Устойчивость

Всё ниже — про то, что происходит, когда что-то идёт не так.

**Драйвер TUN.** Перед подключением клиент проверяет службу `Wintun`. Если
драйвера нет, показывается диалог с предложением установить его: установка
делается тем же ядром на временном профиле (Wintun ставит драйвер при первом
создании адаптера), поэтому ничего не скачивается. Отказ означает, что TUN
недоступен, и приложение предлагает системный прокси.

**Гигиена адаптера.** Wintun не создаёт адаптер, если имя уже занято, а ядро
в этом случае пишет ошибку и **всё равно** поднимает контроллер. Раньше клиент
считал это успешным подключением: счётчики стояли, внешний адрес не появлялся.
Теперь адаптер удаляется перед запуском и после остановки, а после старта
проверяется, что он действительно создан (по строке в логе ядра и по списку
адаптеров). Если адаптера нет — подключение честно завершается ошибкой.

**Сторож ядра.** Выход процесса ядра и «молчание» контроллера больше не
остаются незамеченными: клиент определяет оба случая и перезапускает туннель
автоматически, с паузами 1/2/4/8 с. После четырёх неудачных попыток он
останавливается и показывает ошибку, а не зацикливается. Автоперезапуск
включается только для туннеля, который уже был поднят: если старт не удался,
повторять его бессмысленно, и пользователь видит сообщение ядра.

**Автозапуск и трей.** Приложение может стартовать вместе с Windows
(`HKCU\...\Run`, правится из настроек и видно в диспетчере задач) и по
закрытию окна сворачиваться в трей вместо выхода — соединение при этом не
рвётся. Значок в трее показывает состояние и текущую локацию; выход — через
его меню.

**Маршрутизация загрузок.** Правила в `lib/core/mihomo_config.dart` отправляют
напрямую торренты, Steam и обновления системы, чтобы они не занимали туннель
и не считались в лимит подписки. Игровой режим добавляет к ним игры и
лаунчеры; всё остальное идёт через сервер.

**Свои домены и российские сервисы.** Два независимых набора правил стоят перед
общим `MATCH: свой список обхода из настроек и возврат российских сервисов на
домашний адрес вместе со всей зоной `.ru`. Порядок здесь и есть поведение:
правило, стоящее ниже, никогда уже не выполнится, поэтому обход пользователя идёт
первым, а `MATCH,PROXY` — последним. Наборы переключаются выбором режима в
«Настройках подключения» и применяются к живому соединению через контроллер ядра,
без переподключения.

> Блокировка рекламы из клиента убрана: фильтрующий DNS ломал резолвинг на сетях,
> где его endpoint недоступен, а правила `REJECT` не убирают рекламу из
> приложений, которые отдают её с того же CDN, что и контент (YouTube). Оставался
> вред без пользы. На Android рекламу в YouTube убирает сам YouTube Premium.

**Возврат входа из браузера.** Windows запускает клиент по ссылке
`scaleguard://…` из браузера как обычный процесс. Если в настройках включён
запуск от администратора, этот процесс не становится приложением: он просит
службу-помощника поднять копию с правами, а у запланированной задачи одна
фиксированная командная строка, в которую аргумент браузера не помещается.
Поэтому ссылка сначала передаётся уже запущенному окну через loopback-порт
(и оно разворачивается из трея), а если приложения нет — сохраняется в
`%APPDATA%\ScaleGuard\pending-deep-link.txt` и подхватывается новой копией.
Файл одноразовый и старше десяти минут игнорируется.

## Известные ограничения

* **Только x64.** Ядро собрано под `windows/amd64`; для ARM64 Windows нужно
  добавить `GOARCH=arm64` и соответствующий раннер.
* **TUN требует прав администратора** — это ограничение Windows, а не клиента.
  Оба популярных клиента (Clash Verge Rev, FlClash) решают его установкой
  привилегированной службы-помощника; ScaleGuard делает то же самое
  планировщиком задач (`ScaleGuard Helper`), поэтому повышение прав
  запрашивается один раз, а не при каждом запуске.
* **UWP-приложения не видят loopback** без
  `CheckNetIsolation LoopbackExempt`. Актуально только для режима системного
  прокси; в TUN-режиме проблемы нет.
